## 要点

1. **第 1 条定为 P2 的理由**：服务商的普通错误（401、429、网络失败）走的是逐条 chunk 下发，不进请求级重试。只有以下基础设施错误会进入请求级重试，而且必须和引擎错误在约 0.5–2 秒的窗口内先后出现，才会触发：
   - `network/port-disconnected`（Service Worker 重启）
   - `internal/*`
   - `rate-limit/port-busy`

   一旦触发，后果是悄无声息地丢掉视口内的第一批译文，状态仍显示「完成」。切换引擎和「重试失败」都救不回来。
   同源的两个疑似问题（读代码推断，未复现）：
   - 重试等待期间被 `forget` 的段落会被重新发送（复活）。
   - 等待期间视口重新上报，会导致同一批重复请求。
2. **第 2 条定为 P3 的理由**：旧流程在 epoch 变化之后，实际能抛错的只有 `getConfig`（读 `storage.local`）。它几乎只会在扩展上下文失效时失败，而那种情况下新会话本来也会失败。
3. **第 3 条新发现的现象**：新内容如果追加到一个尚未扫描完的祖先容器里（例如 feed 追加新条目），新的块级子元素会被当成行内内容，并进父容器的 run 里，例如 `<t0><t1>…</t1><t2>…</t2></t0>`。结果是译文插入位置和排版出错。把观察器的注册提前到扫描之前，可以一并修掉。
4. **第 4 条的次生问题**：首次读取失败后，已经被推送过来的配置不会被清掉，订阅也不会恢复，之后会一直用这份过期配置。
5. **Codex「验证记录」的可信度**：总体可信，有两点要注意：
   - 它的复现副本 `/tmp/easy-review-audit` 是复制当时有未提交改动的工作区得到的，不是干净的 `dd5d58b`。不过涉及的文件和基线一致，不影响结论。
   - 它的测试断言的是「当前的错误行为」，所以是绿的，不能直接用作回归测试。
