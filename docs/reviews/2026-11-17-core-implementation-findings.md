# 核心实现复核问题清单

日期：2026-11-17  
审查基线：`dd5d58b`，分支 `feat/phonetics-en`。审查时音标功能仍在并行开发，工作区有未提交修改；以下问题不依赖音标实现。修复前请重新确认当前代码和工作区状态。

本清单基于静态分析及隔离临时副本中的针对性测试。优先级表示影响和处理顺序，不表示已经评估过线上发生频率。没有修改业务代码或项目现有测试。

## 1. 延时重试期间发生引擎错误，段落永久漏译

**优先级：P1；已用会话级测试复现。**

- 位置：`src/content/session.ts` 的请求完成处理和 `onRequestError`（约第 393、435 行）。
- 触发：至少两个翻译请求在途。请求 A 因连接中断等请求级错误进入延时重试；定时器触发前，请求 B 因密钥无效等引擎级错误暂停会话；待 A 的定时器触发后，再切换引擎恢复翻译。
- 原因：A 的未回答段落已从 `sent` 移除。定时器发现 `engineError` 后直接跳过，既不重发，也没有把这些段落放回 `pending` 或 `failed`。切换引擎后，这批段落不再被调度。
- 验证：在临时副本构造 51 个段落产生两批请求，先让第一批连接失败，再让第二批触发 `provider/unauthorized`；等待重试定时器后切换 Google，确认第一批没有被重新发送。
- 建议：暂停期间保留待重试段落，并在恢复后重新调度；修复时同时考虑段落已移除、会话已停止及重复重试的情况。增加上述顺序的回归测试。

## 2. 旧启动流程失败会停止新会话

**优先级：P1；已用会话级测试复现。**

- 位置：`src/content/session.ts` 的 `start` 异常处理（约第 599 行）。
- 触发：第一次启动正在等待配置读取；用户停止并重新启动翻译；新会话已启动后，第一次配置读取才失败。
- 原因：旧调用的 `catch` 只判断全局 `phase !== 'idle'`，随后调用 `stop()`，没有确认当前会话仍属于该次启动，因此会停止新会话。
- 验证：控制第一次 `getConfig()` 延迟拒绝，停止并启动第二次后再释放该拒绝；观察到第二次会话变为 `idle`。
- 建议：将失败清理与相应启动的 epoch 绑定，避免过期启动流程清理新会话；同时保留当前启动失败时的页面清理行为。增加交错启动／停止及延迟失败的回归测试。

## 3. 初次扫描窗口内的动态内容可能漏译

**优先级：P2；扫描器层面已复现，完整浏览器链路待补测。**

- 位置：`src/content/session.ts` 的首次 `discoverUnits` 和随后注册的 `watch`（约第 648、655 行）；`src/content/discover.ts` 的分片遍历（约第 66–86 行）。
- 触发：初次扫描主动让出主线程期间，网页向已经扫描完成的子树新增内容；这次变动发生在 MutationObserver 注册之前。
- 原因：初次扫描不是页面快照，也没有提前记录该时间窗口的 DOM 变动。已扫过的子树新增内容不会出现在扫描结果中，观察器也收不到这次变动，可能一直保持原文，直到后续变化触发重扫。
- 验证：临时副本中让 `discoverUnits` 在首次 yield 时向已扫描的第一个子树插入段落，确认返回结果不包含新段落；结合会话代码确认观察器在扫描完成后才注册。此验证尚未覆盖真实 Chrome 中的端到端时序。
- 建议：在首次扫描前开始记录变动，扫描完成后合并处理，或采用其他能关闭观察盲区的方案。需考虑停止／重启、观察器自身产生的变动和重复注册；补充会话级测试及真实浏览器动态页面验收。可纳入已规划的 M3d。

## 4. 划词配置首次读取可能覆盖更新后的设置

**优先级：P2；已用划词观察器测试复现。**

- 位置：`src/content/selection/watch.ts` 的 `ensureConfig`（约第 203–212 行）。
- 触发：首次选词时，配置读取尚未返回；订阅先收到较新的设置，例如 `showDot: false`；随后旧读取结果返回 `showDot: true`。
- 原因：`config ??= await deps.getConfig()` 在等待前已判断需要赋值，即使等待期间订阅回调更新了 `config`，旧结果仍会覆盖新值。新设置可能一直不生效，直到后续再次收到配置更新。
- 验证：延迟首次配置读取，在其间通过订阅关闭小点，再返回开启小点的旧配置；观察到 `onCandidate` 仍被调用。
- 建议：读取完成后重新判断是否已收到更新，再决定是否采用读取结果；补充上述竞态及读取失败后的订阅行为测试。

## 单独评估：Google 备用接口的限流信号

`src/lib/translate/providers/google.ts` 的 `retryEchoed` 在备用接口返回 429 时保留主接口结果，并停止本批后续备用重试；现有测试明确覆盖了该行为。由于错误没有传到调度器，调度器不会依据该次 `Retry-After` 对其他 Google 请求冷却。

这是**已确认的行为和潜在优化点，不作为已确认产品缺陷**：主接口和备用接口是否应共享冷却范围尚无证据。若实际观察到持续限流，可评估如何保留已有结果的同时传递限流信号，并用多批次测试确认不会过度暂停正常请求。
